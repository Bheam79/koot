## New findings observed in this run

### A. `extractError` is duplicated 3 times in the frontend

**Files:**
- `frontend/src/stores/auth.ts` lines 178-195 (and called at 81, 104)
- `frontend/src/views/ChangePasswordView.vue` lines 19-32 (called at 56)
- `frontend/src/views/ResetPasswordView.vue` lines 21-34 (called at 57)

**The issue:** the same ~17-line helper that turns an Axios error into
a human string (handle `{ error }`, `{ title }`, `ValidationProblemDetails`
`{ errors }`, plain string bodies, and a fallback) is copy-pasted into
three places. A fourth, *abbreviated* form is then sprinkled in seven
more files as inline expressions:

```
$ grep -rn 'response?.data?.error ?? err.message' frontend/src/
frontend/src/views/DashboardView.vue:20
frontend/src/views/DashboardView.vue:34
frontend/src/views/HistoryView.vue:35
frontend/src/views/SessionDetailView.vue:45
frontend/src/views/SessionDetailView.vue:125
frontend/src/components/ImageUpload.vue:56
frontend/src/views/QuizEditorView.vue:340
```

So 10 distinct call sites share a 17-line helper, and a non-trivial
subset of them silently drop the `ValidationProblemDetails` /
`{ title }` branch. A future tweak to error formatting (e.g. toast vs
inline, or adding a `code` field) has to be applied in all 10.

**Fix:** move the canonical implementation into
`frontend/src/utils/apiError.ts` (or `composables/useApiError.ts`),
export a single `extractApiError(err, fallback)` and `toastApiError(err,
fallback)` helper, delete the three copies, and replace the 7 inline
ternaries. ~30 lines of net deletion, plus a new test
`__tests__/apiError.test.ts` covering all the error shapes the backend
actually emits.

**Why this is high-reward:** cheap (a few hours), pure refactor, zero
behaviour change, removes a class of "I forgot to handle ValidationProblem"
bugs. No backlog task covers it.

### C. No backend test for `GameCleanupService`

**File:** `backend/Koot.Api/Services/GameCleanupService.cs`. No
corresponding test file.

**The issue:** the cleanup runs every 30 minutes and is the only
mechanism that turns abandoned `Lobby` / `InProgress` sessions into
`Finished`. A regression (e.g. a wrong `Where` clause or a missing
`SaveChangesAsync`) wouldn't surface in dev — the local dev session is
never 24h old. Production damage is silent: orphaned in-memory state,
sessions in the wrong status, history view showing half-finished games.

**Fix:** test the time-based predicate (`Where(s.Status != Finished &&
s.CreatedAt < cutoff)`), the per-session status mutation, the
`_stateService.RemoveSession` call, and the no-op path when nothing is
stale. Use a real `AppDbContext` against an in-memory or
SQLite-in-memory provider, plus a mock `GameStateService`. ~10 tests,
~150 LOC.

### D. Frontend `logout()` doesn't revoke the server-side refresh token

**File:** `frontend/src/stores/auth.ts` lines 109-111:

```ts
function logout() {
  clearSession()
}
```

The store just clears `localStorage`. The refresh token stored in the
DB (introduced in KOOT-24) outlives the UI session and remains valid
until its 30-day expiry. If the user logs out on a shared device, the
next person to use the same localStorage state still has a valid JWT
*and* a valid refresh token — wait, no: `localStorage` is per-browser
profile, so this is mostly fine. **But** if a user *changes their
password* (KOOT-25) without logging out elsewhere, the in-DB refresh
tokens from other devices are correctly revoked server-side — yet if
they just click "Log out" once, the in-DB refresh token stays
*un-revoked*. An attacker who scraped the refresh token (e.g. via a
backup) can still exchange it for a fresh JWT for up to 30 days.

**Fix:** add `POST /api/auth/logout` (revokes the supplied refresh
token — straightforward given the existing `RefreshTokenService` /
`AuthController` patterns). Frontend `logout()` calls it
(fire-and-forget; don't block the UI on a 4xx) before `clearSession()`.
The endpoint is also a prerequisite for the planned
"Revoke all sessions" UI (none today).

**Why this is high-reward:** small but real security gap, and the
backend half is tiny (≤ 30 LOC) thanks to the existing refresh-token
table.
