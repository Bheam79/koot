## High-reward candidates (ranked)

### 1. Secure the image-upload pipeline (security + correctness)

**Files:** `backend/Koot.Api/Controllers/UploadsController.cs`,
`frontend/src/components/ImageUpload.vue`, `Koot.Api.csproj`.

**What's missing:**
- The only validation is the browser-supplied `Content-Type` header and
  `Path.GetExtension(file.FileName)`. Both are attacker-controlled. A hostile
  client can upload `evil.php` with `Content-Type: image/jpeg` and the server
  will write it as `wwwroot/uploads/evil.php` (the extension fallback takes the
  *content-type* that the attacker supplied). If the host is ever
  misconfigured to execute PHP, this is RCE.
- No actual image inspection. A PNG file that contains HTML/SVG is written
  as-is and served under `/uploads/`.
- No re-encoding. EXIF metadata is preserved, leaking camera serials, GPS
  data, etc.
- No CSP for the served uploads.
- `auth.inferred` partition (current unauth check) is used when the user is
  *not* authenticated; the rate-limiter comment in `Program.cs` notes this
  but the writer still allocates `/uploads/<guid>.jpg` keys with no
  user-association, so a deleted user leaves orphaned files forever.

**Suggested fix (would be a Code task, not a Plan):**
- Add `SixLabors.ImageSharp` (or `Magick.NET`) and re-encode every upload to
  a canonical format (strip metadata, normalize dimensions, cap pixel
  area).
- Use a server-side `signature` check from the decoded image bytes, not the
  client header.
- Move uploaded files outside `wwwroot` and serve them via an auth-gated
  endpoint that streams from blob storage or a static file middleware off
  the public root.

**Why this is high-reward:** existing backlog tasks are all feature-side;
this is the only "real vulnerability" on the radar. KOOT-18/31/32/33 don't
touch it.

### 2. QuestionResults.vue bar chart is fake (UX correctness)

**Files:** `frontend/src/components/game/QuestionResults.vue`,
`backend/Koot.Api/Services/GameStateService.cs` (around `EndQuestionAsync`),
`backend/Koot.Api/Dtos/Games/AnswerResultDto.cs`.

**The issue:** There's a TODO-equivalent in the source comments:

```ts
// We don't have per-player option data here, only isCorrect.
// Show correct vs incorrect breakdown per option slot using the question's
// answer options.
```

The current implementation groups answers into "correct" vs "incorrect"
buckets and then assigns the *correct* bucket to *every* option that's
marked correct and the *incorrect* bucket to *every* option that isn't. So
in a 4-option MC question where 10 players picked A and 5 picked C, the
host sees two adjacent bars showing the same number twice. The displayed
chart is mathematically wrong — it adds up to more than the player count.

**Fix:** Add `OptionDistribution` (already exists for analytics in
`SessionDetailDto`) to the live `QuestionEnded` broadcast. The backend
already loads the answers in `GameStateService.EndQuestionAsync` — just
group by `AnswerOptionId` like the analytics endpoint does and include
`{ optionId, pickCount }[]` in the broadcast. Frontend updates the bar
chart to use the new field.

**Why this is high-reward:** hosts rely on the breakdown to settle
disputes about scoring during a live game. A wrong chart is worse than no
chart. Distinct from KOOT-33 (which is about new question types, not
fixing existing ones).

### 3. Consolidate the duplicated `QuestionType` enums (DX / maintenance)

**Files:** `frontend/src/types/quiz.ts` (defines `QuestionType`),
`frontend/src/types/game.ts` (defines `QType` with the same int values),
`frontend/src/components/game/PlayerQuestion.vue` (imports `QType`).

**The issue:** two `const` objects with identical keys and values represent
the same backend enum. Renaming/reordering on either side risks silent
drift. The CLAUDE.md note in the project root even calls out the
`erasableSyntaxOnly` workaround for the backend's enums. The frontend has
solved the same problem once, but `QType` was duplicated instead of
re-exported.

**Fix:** delete `QType` from `types/game.ts` and re-export `QuestionType`:
```ts
export { QuestionType as QType } from './quiz'
```
…or, better, rename `QType` call sites to `QuestionType` and remove the
duplicate. ~5-line change.

**Why this is high-reward:** cheap, eliminates a class of "uint 4 vs 5"
bugs that would be invisible until a question type was added. No backlog
task covers this.

### 4. Backfill unit tests for the untested controllers/services (coverage)

**Currently tested:** `AuthController`, `QuizzesController`,
`GamesController` (history), `JwtService`, `PasswordManagement`,
`RefreshToken`, `RateLimiting`, `GameService` (pure), `GameStateService`
(in-memory parts).

**Tested by E2E only:** `QuestionsController`, `UploadsController`,
`GameHub`, `GameCleanupService`.

**Notably uncovered behaviour:**
- `ValidateQuestionPayload` table in `QuestionsController` — 4 question
  types × multiple failure modes × the auto-synthesised `TrueFalse`
  options. A subtle regression here lets invalid quizzes persist.
- `BuildAnswerOptions` `TrueFalse` synthesis: the `IsCorrect` heuristic
  uses `first.Text` to decide which side is correct — there is no test
  for the "first option is neither 'True' nor 'False'" branch.
- `GameHub.SubmitAnswer` correctness logic via `DetermineCorrectness`:
  - `TypeAnswer` with surrounding whitespace / multiple accepted
    answers — only `OptionDistribution` "first" is considered.
  - `Poll` returns `false` even when the question type is wrong.
- `UploadsController` rejects oversized / wrong-type files; **no tests**
  verify the size cap, the content-type / extension mismatch handling,
  or the response shape.
- `GameCleanupService` — no tests at all (it runs every 30 minutes; an
  EF Core stop-the-world regression would surface 30 minutes later).
- `GameStateService.EndQuestionAsync` / `EndGameAsync` — the
  timer-cancellation race; the leaderboard top-10 truncation; the
  removal of the session on end.

**Fix:** ~6 short test files mirroring the existing patterns. Coverage
threshold is already 50% in `vite.config.ts`; backend has no enforced
threshold. A reasonable target is to add ~30 tests covering the
branches above, lifting the backend line-coverage from an estimated
~55% to ~80%.

**Why this is high-reward:** every other Plan task is a feature; this is
the only one that meaningfully de-risks future changes. Distinct from
KOOT-31/32/33 which are net-new features.

### 5. Add a backend test layer for the SignalR hub (currently E2E-only)

**Files:** `backend/Koot.Api/Hubs/GameHub.cs`,
`backend/Tests/GameStateServiceTests.cs` (already exists, in-memory only).

**The issue:** The `SubmitAnswer` hot path is currently only exercised
through `playwright` E2E tests, which require a live backend + MariaDB.
They take 5-10 seconds per spec and are flaky when the websocket
handshake times out. The pure-CPU parts of `GameHub` (the correctness
check, the score calculation, the duplicate-submission guard, the
question-id mismatch) can be tested directly with Moq over the
`HubCallerContext` and an in-memory `AppDbContext`.

**Fix:** extract `GameHub.DetermineCorrectness` (already private
static) into a public static helper that tests can call directly. Add
~15 tests covering the answer-dispatch logic. Then the E2E suite can
shrink to one happy-path spec (the full-WS round-trip) and the rest
moves to fast in-process tests.

**Why this is high-reward:** the current E2E suite is the only thing
exercising the live game flow. Build times and CI flakiness scale with
E2E count. Move fast tests to fast tests.

## Lower-priority observations (for completeness, not proposed as tasks)

- Frontend `Logout` clears localStorage but never calls the backend; the
  refresh token in the DB outlives the UI session. Adding
  `POST /api/auth/logout` (revokes the current refresh token) is a small
  follow-up.
- `AppDbContext` has no global query filter for `IsDeleted` (none
  defined; future soft-delete would need a migration).
- Frontend `QuestionType` (in `types/quiz.ts`) hardcodes 4 type values;
  when KOOT-33 lands, that file becomes the source of truth — the
  duplication noted in #3 above would multiply.
- `BCrypt` work factor is 11 (default). For new hashing on high-value
  targets 12+ is recommended; measure login latency first.
- `appsettings.json` `Jwt:Key` is a placeholder string committed to the
  repo. A `IConfiguration` test that the key is overridden in

  the comment in the file) — fine for now, but if a design system is
